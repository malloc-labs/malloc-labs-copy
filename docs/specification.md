# Copy — Specification

Version 0.1.0

This document specifies Copy v0. It assumes `philosophy.md` and refers to it by section number where appropriate.

---

## 1 System Overview

Copy comprises two parts:

- **Engine** — a headless Python process that owns audio output, MIDI input, sequence generation, timing, and truth recording.
- **UI** — a static browser surface that controls the engine and renders post-session review.

The engine and the UI are separated from the start. The engine never imports the UI; the UI never reaches into engine internals. They communicate over HTTP and WebSocket on localhost.

### 1.1 Why this shape

This separation gives two properties that matter for the project's long-range path:

- The same engine can run on a desktop, a Pi, or a future standalone listen device without architectural change. Only the UI shell varies, or is omitted.
- The browser tab can lose focus, minimise, or close mid-session and the listening continues. Audio is generated and emitted by the engine, not the browser. The "screen is not the protagonist" contract (philosophy 3.1) holds at the architecture layer, not only at the UI layer.

### 1.2 The Pi-class yardstick

Every feature should pass the question: *could this run on a Pi-class device?* If the answer requires GB-scale memory, a heavy framework, or significant CPU, the design needs reconsideration. The yardstick is checkable; abstract architectural principles are not.

### 1.3 Deployment shapes

| Shape | Engine | UI | Audio out | MIDI in |
|-------|--------|-----|-----------|---------|
| **v0 desktop** | learner's machine | browser tab on same machine | machine's audio jack | USB-MIDI to engine's machine |
| **Future Pi build** | a Pi | browser tab on phone or laptop on the local network | Pi's audio jack | USB-MIDI to the Pi |
| **Future standalone** | the standalone host | none, or a small physical UI | host's audio | USB-MIDI to the host |

v0 only commits to the first row. The other rows are guard-rails for "are we coding ourselves into a corner?"

### 1.4 Touch points and transition zones

The engine ↔ UI boundary is a touch point: a narrow, deliberate channel. Two other touch points exist in v0:

- The **MIDI port** — between the learner (paddle/key) and the engine. The vocabulary is defined in §3.
- The **paper notebook** — a transition zone between analog cognition and digital truth (philosophy 3.8). The software has no awareness of it; it is the learner's.

The risk space is the *gap* between zone and touch point — between hearing-and-writing, between writing-and-keying. Coordination across that gap is part of the skill being trained, not a friction to engineer away.

### 1.5 Error handling philosophy

The honesty contract (philosophy 3.4) extends to failure modes. When something goes wrong — the MIDI device disconnects mid-session, the audio device fails, a phonetic anchor file is missing — Copy surfaces the failure plainly.

- No silent retries that hide a problem from the learner.
- No fallback behaviour that pretends to continue (e.g. recording marks against truth while audio is no longer playing).
- The failure state is visible in the UI; the engine logs the cause; the session is closed honestly rather than partially recorded.

The principle that governs verification — say only what is true — governs failure too: the system says what failed, when, and stops doing what it cannot truthfully do.

### 1.6 Logging

The engine writes a local log file for development and diagnostics:

- Default location follows the malloc-labs host convention (`/srv/work/malloc-labs/logs/copy_653/copy_653.log`), rotating by date. On a developer machine without that host layout, defaults to `~/.local/share/copy_653/logs/copy_653.log`.
- Log level configurable (default `INFO`); `DEBUG` for development.
- The log is engine-only — it is not surfaced in the UI and is not part of session records.
- No telemetry. The log file never leaves the local machine.

The log exists so the developer (the learner, in the dogfooding case) can diagnose engine behaviour. It is not a learner-facing feature.

## 2 Audio Specification

### 2.1 Tone generation

A single sine-wave tone, gated by an envelope, generated by the engine and emitted via the host's audio output. The engine emits mono samples and lets the OS handle stereo duplication.

### 2.2 Defaults

| Parameter | Default | Rationale |
|-----------|---------|-----------|
| **Koch character speed** | 20 WPM | Koch original; comfortably above the counting threshold (~18 WPM). |
| **Tone frequency** | 600 Hz | De facto standard. |
| **Farnsworth effective speed** | 10 WPM | Wide spacing for thinking time *between* shapes without contaminating shapes themselves. |
| **Sample rate** | 48 kHz | Common, low resampling friction. |
| **Tone amplitude** | 0.3 | Approximately -10 dB FS — quiet by default to protect headphone users from a sudden full-scale tone. See §2.7. |

All of the above except sample rate are exposed as learner-configurable settings in a config file. The Settings page surfaces the two timing controls first: Koch WPM (`character_speed_wpm`) and Farnsworth WPM (`effective_speed_wpm`). Other audio knobs remain config-file settings.

### 2.3 Envelope

The on/off transitions of the tone use a raised-cosine envelope (default ramp time 5 ms) to avoid keyclicks. Sharp on/off generates broadband artefacts; the envelope is small but its absence is audible. The envelope is not a learner setting.

### 2.4 Character speed: a narrow useful band

Character speed is not the primary difficulty knob.

- Below ~18 WPM the brain has time to consciously count dits and dahs, and the decoder being trained is the wrong one.
- Above ~25 WPM the learner is at performance speeds rather than learning speeds.

Difficulty adjustment in Copy happens through:

- **Farnsworth spacing** — wider spacing means more thinking time without changing shape recognition.
- **Signal condition** — clean → static → fading → fist variation (philosophy 3.5). The signal-complexity axis is the working axis.

Apps that promise easier learning by lowering character speed below the counting floor are answering the wrong question. Copy does not.

### 2.5 Symbol set

The symbol set in any stream is gated by what the learner has claimed competence in (philosophy 5). The v0 starting set is **K and M** (the canonical Koch first pair). Unknown symbols never enter the stream.

### 2.6 Phonetic anchors

Each symbol the learner can encounter has a paired audio file containing the spoken NATO phonetic anchor (philosophy 3.2). For v0, the two required files are "Kilo" and "Mike". Anchors are short audio files (WAV or similar), not synthesised speech, so the recorded voice is consistent and the audio quality is controlled.

The v0 anchors will be recorded by an experienced radio operator. Until those recordings land, temporary placeholder audio is used so the engine's playback path can be developed against something real. Placeholders are replaced before any release outside dogfooding.

### 2.7 Amplitude and hearing safety

The synthesised tone is generated at a default amplitude of 0.3 (approximately -10 dB below digital full-scale), well below the maximum the audio device could produce. This is deliberate.

A learner using headphones at unity system volume should not be exposed to a sudden full-scale tone. Synth content (a sustained pure sine) is harsher on the ear than music at the same digital level because there is no transient masking, and Copy is run for long sessions in close proximity to the ear. The amplitude default is chosen to be quiet enough to be safe even at high system volume; the expectation is that the learner adjusts hardware volume — interface, headphone amp, system — to a comfortable listening level, not the other way around.

Amplitude is configurable via `AudioParameters.amplitude` for learners who want to tune it (within the valid range `(0, 1]`). The configured value is the *peak* sine amplitude before the envelope is applied; with the raised-cosine envelope the perceived loudness is slightly below the peak.

Copy does not implement dynamic gain control, limiting, normalisation, or auto-adjustment. The honesty contract (§1.5) extends to volume — what is configured is what is produced.

The output device is selected via `AudioParameters.output_device`: `None` for the system default, an integer for a sounddevice device index, or a substring of a device name (e.g. `"Mac mini Speakers"`). On macOS, sounddevice writes via the CoreAudio HAL directly and bypasses the consumer mixing graph that per-app routing utilities (SoundSource, BlackHole, etc.) hook into. As a result, those utilities cannot see Copy's audio. The volume controls that *do* apply are the configured amplitude, the audio interface's hardware level, and (where the device exposes one) the operating-system master output. Pinning `output_device` in the configuration removes any dependence on the system default-output state at run time.

### 2.8 Sequence generation

The stream of symbols is generated using a per-session pseudo-random number generator scoped to that session:

- The engine creates a `random.Random()` instance at session start.
- The session-scoped instance is used for all sequence generation.
- The module-level `random` state is never modified. Other libraries in the engine process are not affected by Copy's sequence generation.
- The seed is recorded in the session record; a learner can replay the same stream by re-running with the same seed.

Distribution is uniform random across the known symbol set. Forced balance (e.g. exact 50/50 K/M) is not applied — forced balance is itself an artefact, and natural CW does drift. Long runs (KKKKK or MMMMM) are permitted because they occur in real CW and the learner has to handle them.

Constraints may be revisited if dogfooding reveals specific pathological cases. None are imposed in v0.

## 3 Input Model

### 3.1 Hardware contract

The engine reads MIDI directly from any class-compliant USB MIDI device. The reference device is the Adafruit TRRS Trinkey running CircuitPython firmware (§7); other devices that present as USB MIDI work without changes.

MIDI never crosses through the browser. The browser does not need Web MIDI API support. The engine ↔ paddle channel is a single touch point.

### 3.2 Vocabulary of named events

The engine listens for a vocabulary of *named events*, not specific MIDI messages. The mapping from MIDI input to named event is configurable per learner.

| Event name | Meaning | Where active |
|------------|---------|--------------|
| `mark` | "I heard the target here" | Detection sessions |
| `confidence` | A confidence/uncertainty marker | Any listening mode |
| `suspected-cq` | "I think a CQ call happened here" | Detection sessions; future use |
| `replay` | Mark this segment for replay during review | Any time |
| `scrub` | Move the playhead during review | Post-session review |
| `loop-on` / `loop-off` | Start/stop a temporary loop on a segment | Post-session review |

This vocabulary is intentionally extensible. Adding a new named event does not require rebinding existing devices.

### 3.3 Default MIDI mapping

| MIDI input | Named event |
|------------|-------------|
| Note 60 (note-on) | `replay` |
| Note 61 (note-on) | `suspected-cq` |
| Note 62 (note-on) | `confidence` |
| Note 64 (note-on) | `mark` |
| Control Change 1 (CC1, value 0–127) | `scrub` (value maps to playhead position) |
| Sustain pedal (CC64) on | `loop-on` |
| Sustain pedal (CC64) off | `loop-off` |

Velocity is captured but is not consulted by v0 logic. A future version may use velocity as a confidence weighting; the schema accommodates this without change.

The mapping lives in a configuration file the learner can edit. An in-app rebind UI is not v0.

### 3.4 Same surface during listening and review

The MIDI device is the learner's primary low-overhead interaction with Copy *throughout the session, including review*. Hands stay on the paddle/keys; the screen and keyboard never become the protagonist at any point. The philosophy 3.1 contract is carried through to the review surface.

## 4 Mode Behaviour

The three modes (philosophy §4) are realised as follows.

### 4.1 Introduction

Sequence: spoken NATO phonetic anchor → short pause → CW pattern → long pause. Repeat for the requested symbol set.

- No claim, no marking, no verification.
- No timer; the learner stops when they choose.
- The UI shows only a "stop" affordance; everything else is audio.

### 4.2 Detection

Stream of known symbols of configurable duration (default 2 minutes). The learner copies into their paper notebook (the canonical capture) and may optionally send `mark` / `confidence` / `suspected-cq` events via the paddle.

The engine records:

- The full sequence sent, with timing.
- The complete stream of MIDI events received, with timestamps.

Post-session, the UI exposes:

- The sent sequence on a timeline.
- The learner's MIDI events overlaid on that timeline.
- No score. No commentary. Hits, misses, and false positives are visible by inspection.

The active-acknowledgement layer does not turn Detection into a transmission trainer (philosophy 4.2). Send and receive remain different domains.

### 4.3 Full Copy

Stream of known symbols of configurable duration. The learner copies into their paper notebook. The MIDI device may be used for `replay` and `confidence` markers if desired.

The engine records:

- The full sequence sent, with timing.
- Any MIDI events received, with timestamps.

Post-session, the UI exposes:

- The sent sequence as text and as a timeline.
- The audio is replayable in full or by segment via the paddle's `scrub` and `loop-on`/`loop-off` events.
- The learner reflects against their own paper. The software does not capture, transcribe, align, or grade the notebook (philosophy 6).

## 5 Truth and Review

### 5.1 What the engine records

For every session:

- The full symbol sequence sent (the truth).
- The audio parameters used (character speed, tone, Farnsworth, condition).
- Timestamps for every symbol on/off boundary.
- Every MIDI event received, with timestamps.
- Session start and end wall-clock times.

That is all. No biometric capture, no learner identifier beyond the local user account, no telemetry to any external service.

### 5.2 What the UI exposes during review

Review presents the session as a timeline. The truth is rendered plainly. Marks are overlaid. The learner can:

- Replay any segment via paddle-driven `scrub` and `loop-on`/`loop-off`.
- Read the truth as text.
- Close the review.

What review does not do:

- Score the session.
- Grade the notebook (the engine does not see it).
- Comment on hit rate.
- Compare against prior sessions.
- Encourage, congratulate, or commiserate.

The honesty contract (philosophy 3.4) is realised in review by silence around everything that is not literal truth.

### 5.3 The honesty contract in numbers

If the learner sent 7 marks and the stream contained 12 instances of the target, the review shows 7 marks and 12 instances, displayed plainly on a timeline. There is no derived percentage, no streak, no grade.

## 6 Persistence

### 6.1 What is persisted

- **Session records** — one file per session, containing the truth, parameters, MIDI events, and timestamps. Format: JSON, on local disk.
- **Configuration** — the learner's audio parameters, MIDI mapping, and claimed symbol set. Format: TOML, on local disk.

### 6.2 What is not persisted

- No user account, login, or remote storage.
- No scores, streaks, completion percentages, or progression metrics.
- No analytics, telemetry, or session counters reported anywhere.
- No notebook content (the notebook is paper).

### 6.3 Storage location

Default: `~/.local/share/copy_653/` on Linux/macOS and the platform equivalent on Windows. Configurable.

### 6.4 The learner can read the files

Both file formats are plain text and inspectable. A learner who wants to write their own analysis tools can. Copy does not consider the storage layer to be hidden infrastructure.

## 8 v0 Scope

### 8.1 What v0 ships

- The engine, in Python, with audio out via PortAudio (`sounddevice`) and MIDI in via `python-rtmidi` or `mido`.
- The UI, as static HTML and vanilla JS, served from the engine on localhost.
- The three modes: Introduction, Detection, Full Copy.
- The K, M Koch starting symbol set.
- A clean signal condition only (no fading, no static, no fist variation).
- The default MIDI mapping per §3.3.
- A single audio file pair for the K and M NATO phonetic anchors ("Kilo", "Mike").
- Session records persisted to local disk.

### 8.2 What v0 does not ship

- Additional Koch pairs beyond K, M.
- Signal complexity (fading, static, fist variation, weak-signal emergence).
- A learner-rebindable MIDI mapping UI (the mapping file is hand-editable; an in-app rebind UI is later).
- Trinkey firmware (until the device arrives — §7).
- A standalone listen device.
- Multi-learner support.
- Any kind of native mobile application.

### 8.3 Listening screen affordance budget

The listening screen (Detection or Full Copy) shall not exceed five visible affordances. If a sixth proposes itself, something else gives way. This is a hard ceiling, not a guideline.

## 9 Non-Goals

The following are explicit non-goals. Their presence in any future iteration is grounds for re-reading this document.

- Scoring, grading, percentages, streaks, badges, levels, achievements, or any progression metric.
- Leaderboards, user profiles, social features, sharing, or community surfaces.
- Hint systems, encouragement copy, manufactured warmth, congratulations, or commiserations.
- Real-time correctness feedback during a listening session.
- Notebook capture, OCR, alignment, transcription, or grading.
- Automatic difficulty adjustment based on learner performance.
- Telemetry, analytics, or any data sent to any service Copy does not control.
- Account systems, login, identity.
- A simulated mentor, tutor, or coach (philosophy 3.6).
- Native mobile applications. The browser may serve mobile-shaped layouts later if useful; native apps are not on the path.

The not-list is part of the specification, not commentary. A pull request that adds any of the above is a contract violation, regardless of how small the addition seems.

### 10.1 Package naming

The Python package name is `copy_653`. The distribution name is `copy-653`.

- The hyphenated form is the project's external name during development; the underscored form is the import name.
- This eliminates any conflict with the Python standard library `copy` module — `copy_653` cannot shadow stdlib `copy`.
- The number 653 is the developer's police service badge number, retained as a personal mark on the project during the development phase.

When the developer obtains a UK amateur radio licence, the package is renamed to `copy_{callsign}` (e.g. `copy_m0xxx`). That rename is a semver MAJOR boundary; installed environments will need to migrate. The friendly product name "Copy" is unchanged by either name.

### 10.2 Host-level conventions

Venv, logs, and runtime data follow the malloc-* host pattern:

- venv: `/srv/work/malloc-labs/venvs/ml-copy-653/`
- logs: `/srv/work/malloc-labs/logs/copy_653/`
- runtime: `/srv/work/malloc-labs/runtime/copy_653/`

These are deployment conventions inherited from the malloc-rubicon host structure, not concerns of the repository itself.

## 11 Distribution and Versioning

### 11.1 Distribution (v0)

v0 distributes by clone-and-deploy using standard pip:

```sh
git clone <repo>
cd malloc-labs-copy
python -m venv .venv
source .venv/bin/activate
pip install -e .
python -m copy_653
```

The engine starts, opens the audio device, opens the MIDI port if available, and serves the UI on a localhost port. The learner opens that URL in a browser.

For deployment alongside other malloc-labs apps, the venv may live at the host-convention path (§10.2) instead of a local `.venv`. `pyproject.toml` follows PEP 621 so contributors who prefer `uv`, `pipenv`, or other tooling are not blocked.

Building a wheel for distribution to PyPI is not v0. It becomes worth doing once a second person installs Copy.

### 11.2 Versioning

Semantic versioning from the start:

- `MAJOR.MINOR.PATCH`
- Tagged on git as `vMAJOR.MINOR.PATCH`
- v0 begins at `0.1.0`. Pre-`1.0` releases may break contracts between minor versions.
- Breaking changes after `1.0.0` bump MAJOR.
- The version is recorded in `pyproject.toml` and included in every session record so a learner reviewing an old session knows which engine version produced it.

### 11.3 Release tooling

- Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `BREAKING CHANGE:` footer) for commit messages.
- Release tagging may be automated via `release-please` or equivalent once the project moves out of single-user dogfooding. v0 may tag manually.

## 12 Frontend Approach

The UI is hand-spun HTML, CSS, and vanilla JavaScript. No build step. No bundler. No transpilation. No CSS framework.

Reasons:

- The app surface is small. A framework is more code than the app.
- A learner inspecting the source can read it directly.
- The Pi-class yardstick (§1.2) is met trivially.
- Updates do not require a node toolchain.

### 12.1 Browser floor

Modern evergreen browsers: current Chromium-based, current Firefox, current Safari. No legacy browser shimming. Web platform APIs are used directly.

### 12.2 Design system alignment

The visual language is aligned to the Malloc Rubicon design system (`~/dotfiles/docs/design/malloc_rubicon_design.md`). Carry-over decisions:

- **No red.** Red creates emotional heat faster than shared understanding. Copy is a learning environment, not an alert system.
- **Structure before emphasis.** If structure is weak, emphasis becomes noise.
- **Mono for evidence, sans for narrative.** Truth display in review is mono; section headings and labels are sans.
- **Self-hosted fonts** (woff2) — Inter (sans), JetBrains Mono (mono). No web-font CDN.
- **Dark theme default**, light theme available.

Copy ships a `core.css` that uses the Malloc Rubicon `--mr-*` token system as its baseline. Outliers — Copy-specific tokens or component classes that do not exist in Malloc Rubicon — live in a sibling `copy-653.css`. Outliers that prove generally useful are fed back into the Malloc Rubicon design doc and graduate from `copy-653.css` into `core.css`.

### 12.3 Crisis Room doctrine applies

Copy's listening and review surfaces follow the Crisis Room behavioural doctrine from the Malloc Rubicon design system:

- The interface must never compete with the event (the listen).
- One signal at a time.
- Return to neutral quickly.
- Evidence (truth display) reads cleanly.
- No decorative urgency.

Failure indicators: the UI is beginning to fail when everything appears important, when warning states persist by default, or when colour is compensating for weak wording.

## 13 Accessibility

Copy is implicitly an accessibility-shaped project. The reference paddle device is the Adafruit TRRS Trinkey, an Adafruit Assistive Technology product. The audio-first / off-screen design principles overlap substantially with low-vision user needs. The MIDI input model permits the learner to use whatever physical input device they have customised for their own use.

### 13.1 Hardware: do not interfere with the learner's setup

The MIDI vocabulary is named events (§3.2), not specific inputs. A learner using a custom-built switch, a sip-and-puff device, or any other class-compliant USB MIDI device that emits the named events works with Copy without modification.

Copy does not assume the learner has two hands, can reach a keyboard, can see a screen, or is using a paddle in any specific physical configuration.

### 13.2 Visual accessibility

- The browser UI uses semantic HTML throughout. Headings are real headings; controls are real controls; tables are real tables.
- Colour is never the sole carrier of meaning (per the no-red rule and the broader Malloc Rubicon design doctrine).
- Light and dark themes are first-class.
- Font sizes use rem units; the learner's browser-level font scaling is respected.

### 13.3 Auditory accessibility — open question

A deaf or hard-of-hearing learner cannot use Copy as currently designed; the entire premise is auditory training. A meaningful accommodation would require visual or tactile signal representation. v0 does not attempt this.

If a deaf or hard-of-hearing learner base emerges, Copy's response is to engage that community directly to design what they actually need, rather than ship a generic accommodation that satisfies industry checklists without serving the user. Industry standards are followed in the meantime as a baseline; they are understood to be necessary but probably insufficient.

### 13.4 Conventions used in the meantime

WCAG 2.2 AA targets where applicable to the visual surface; ARIA where semantic HTML does not carry the meaning. These are not the ceiling, only the current floor.
